# D435 recovery - 2026-11-08

## Cause and recovery

The running camera owner had been launched with `--skip-camera d435`
during the preceding Astra SDK investigation. This explains the current
D435 metadata message "not enabled this session"; it is not evidence of
another current USB disconnect.

Earlier kernel logs did record D435 UVC control failures followed by a USB
disconnect at Nov 7 22:30:16 and re-enumeration at 22:45:37. Those historical
failures are distinct from this temporary skip. Their underlying cable,
power, or driver cause has not been established.

Only the camera capture owner was gracefully stopped and restarted,
without the skip argument. No source change, USB reset, firmware update,
robot driver restart, homing, or motion command was required. No persistent
launcher contains `--skip-camera d435`; the normal launcher enables color
preview for all three cameras and defaults every depth stream to OFF.

## Live verification

Used the existing 9983 `/api/camera/depth` HTTP endpoint with its normal
session cookie and Origin check. Two complete D435 ON/OFF cycles passed:

- Color JPEG: 640 x 480; sequence and capture time advanced.
- Depth: 640 x 480, lossless uint16 PNG; frame numbers advanced 14 to 38
  within each enabled session, with fresh sensor timestamps.
- Depth scale: approximately 0.001 metres per raw unit.
- Depth aligned to color; finite color-projection intrinsics.
- Nonzero depth fraction: approximately 97.3-97.4% in the observed scene.
  This measures pixel coverage, not metric accuracy.
- After each disable: active streams contained only `stream.color` and
  color sequences continued advancing.
- Final HTTP state: all three cameras color_online=true,
  requested=false, state=disabled, active=false. YOLOE remained disabled.
- Robot drivers retained PID/start-ticks pairs 7360/27507,
  7502/27601 and 7650/27696 throughout the camera recovery.
