## TCP

用户确认用于触点标定的尖头就是 CAD 定义的夹持中心。
采用两轮 16 姿态联合结果，右腕 `right_link26` 到夹持中心：
`[148.14204045, 0.18118211, -1.14256599] mm`。
配置在 `config/right-grip-tcp.json`，保留来源文件哈希、求解方法和残差。
两轮触点位置不同，联合求解使用一个共享 TCP、两个独立世界触点。
方向沿用 J6 约 -90 度的 CAD 夹姿约定；触点标定本身不测方向。
计算使用完整旋转变换，不能把 148 mm 直接当作任意姿态下的整车 X 偏移。

## 固定顺序

`agent/battery_flow.py` 调用现有工具注册器，无需 LLM 决定每一步：

1. D435 冻结 RGB-D、识别电池并粗定位，绑定本次目标。
2. 生成升降和观察姿态计划，交给本地路径检查。
3. 通过现有 Controller 执行升降；实测停稳后才执行右臂观察姿态。
4. D405 重新采集，通过识别、FoundationPose、点云得到提手位置和水平线段。
5. 用测得 TCP 换算腕部预抓位，执行并等待反馈停稳。
6. 重新拍摄检查对位，按已有策略进行有限次纠偏；不沿用移动前的画面。
7. 对齐后执行固定 Y/Z、沿 +X 前伸；实测到位后闭爪。
8. 采集闭爪后的新画面，交给抓后核验。闭爪到位不是夹住电池的证据。

一次识别失败会在工具内部有限次重拍。路径不可达、反馈失效、取消、
不明执行回执仍停止本轮，不会换个请求编号偷偷重复动作。
停止后不自动续跑；原请求的已完成回执可恢复，不重新下发。

## 程序入口

`agent/battery_workflow.py::build_workflow(...)` 装配固定流程、执行工具、
`BatteryControllerBackend` 和测得 TCP。构造函数不预占、不启动、不移动设备。
调用者显式传入已占用控制权的 Controller/token、本地参数和检查函数，
再调用返回对象的 `run()`。所有动作仍走原 Controller，不模拟网页键盘，
不新开 CAN/SDK 所有者。任务调用者负责控制权生命周期和停止后的清理。

底层粗调、预抓和前伸闭合均按请求写入执行日志后再调用 Controller。
同一 run 只允许一个固定流程运行者；重复调用已结束流程只返回原结果。

## 本次验证了什么

- 175 项 Agent 测试、281 项 web 测试通过（该记录对应提交前完整回归）。
- 固定流程用替身工具走完一次识别到核验，以及一次重拍纠偏。
- 真实工具注册器接入惰性执行步骤，验证粗调回执、反馈屏障、日志和幂等。
- 验证取消、不明回执、进程阶段恢复、重复调用不会继续或重复运动。
- 验证旧照片、错误目标不能确认抓取，关闭运动配置不能准备动作。
- 验证 TCP 旋转换算及现有真实 URDF/IK 规划测试。

这些是软件证据，不是实车抓取成功率或毫米精度验收。

## 接实车前仍需接入的具体能力

- `review_plan`：对完整计划返回匹配哈希的本地检查证据。
  已有立柱检查不能冒充完整现场障碍物检查，当前没有默认放行函数。
- `preflight`：版本、现场、反馈、控制权、夹爪起始张开状态及运动通道检查。
  本轮复用原前伸闭合步骤，没有新增自动张爪步骤；起始夹爪须已张开。
- `hold_verifier`：对闭爪后新观察给出同一目标的实际夹持证据。
  未配置时明确返回 `awaiting_hold_verification`，不报告成功。
- 9983 的执行入口、这些本地策略的现场配置和实车验收尚未部署。

默认 9983 仍是原预览链路。本次不会通过伪造检查结果让预览直接变成动作。
