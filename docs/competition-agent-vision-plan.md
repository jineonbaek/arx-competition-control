## 1. 一页看懂当前方案

当前决定采用一条分工明确的机器人操作链路：

**Qwen理解指令和视觉目标，深度相机与标定提供三维几何，GraspNet或同类点云抓取模型生成抓取候选，本地规划与厂家接口执行动作。新建任务Agent，通过工具组织这些模块，再根据真实反馈决定下一步。**

这延续了此前ThirdHand“通过工具操作机械臂”的组织思路。对新机器人，需要重新落实X5接口、坐标、夹爪、传感器和底盘适配。

完整比赛的预期目标：**识别并抓取目标电池，稳定携带通过障碍区，到达目标仓，对准插入，释放并保持稳定。**

## 3. 决赛任务与设计目标

### 3.1 本地规则对应的完整任务

本次核对了`赛事资料/2026年挑战赛规则及赛题说明10.22.pdf`第5至7页。该版本描述的决赛为单块电池跨区搬运与目标仓放置：

1. 出发区中识别并抓取目标电池；
2. 携带电池通过障碍过渡区；
3. 到达正确目标仓位；
4. 将电池插入有效范围，稳定释放；
5. 释放后稳定3秒，无滑出、弹出或倾倒。

每轮只搬运一块目标电池。比赛过程中应自主运行，不得人工遥控、扶持或修正电池、路径；不采用抛投、滑送或掉入等方式代替正常放置。

该版规则的分值结构为：抓对25分、走好30分、放好35分、时间效率10分。形态额外加分的适用性由组委会认定，本文不预先认定LIFT2s可获得该项分数。

### 3.2 对系统能力的实际要求

| 任务环节 | 系统需要解决的问题 |
|---|---|
| 识别 | 目标电池和目标仓是否选对，颜色与编号是否对应 |
| 抓取 | 夹爪能否接近、接触并稳定夹住电池 |
| 携带 | 电池在抬起、收臂、底盘运动及越障过程中是否持续保留 |
| 通行 | 路线、障碍物、底盘和整机姿态是否满足任务要求 |
| 对准 | 电池的进入端与仓口位置、轴线、方向是否匹配 |
| 插入 | 是否实际进入目标有效范围，而非仅到达仓口上方 |
| 释放 | 松爪、撤离后电池是否仍留在正确仓位 |
| 完成 | 所需关系是否均得到证据支持，并满足稳定时间要求 |

因此，系统需要优化完整任务的完成质量。抓得起来只是其中一个环节。

### 3.3 赛事资料中的待确认事项

本地资料存在以下差异，不宜直接转成硬编码参数：

- FAQ与10.22版规则中的部分掉落、障碍物扣分值不同。本文按10.22版说明任务结构，具体执裁口径仍应保留最终组委会确认记录。
- 道具参数第1页出现`169.6/2 = 89.8mm`，算式不一致；169.6除以2在算术上为84.8。该问题需要确认设计意图及实物尺寸，不能只把商改成84.8就认定是正确单仓尺寸。
- 道具资料列出了真电池最大约1020g、无配重假电池约100g。测试时应记录实际使用哪一种，不能用轻假电池的结果代表真电池搬运表现。
- 决赛时间限制、允许接触方式、仓位尺寸和现场道具版本，应以最终资料及确认结果为准。此前初赛的建议时长不能直接作为决赛限制。

## 4. 机器人和传感器背景

### 4.1 当前平台

团队已选择方舟无限LIFT2s轮式双臂平台，机械臂资料方向为X5，底盘及升降资料方向为LIFT2。具体设备铭牌、硬件版本、固件和SDK对应关系，实施前需要记录。

车载ROG负责承载本地视觉、点云、规划、任务程序和ROS2等软件。云端只承担选择性模型调用，机器人执行和反馈处理仍保留本地。

此前会话记录的ROG约有8GB显存；本次没有重新连接ROG核查。该记录只能用于初步资源预算，不能作为当前空闲显存或多模型运行能力的证据。

### 4.2 相机布局以用户最新说明为准

本轮采用以下三个机位：

| 机位 | 用户已说明的位置 | 建议用途 | 需确认 |
|---|---|---|---|
| 头部相机 | 头部 | 全局搜索、场景理解、发现电池和作业区域 | 型号、深度、颈部自由度、视野 |
| 胸前相机 | 胸前 | 桌面工作区观察、抓取主视角候选 | 深度质量、升降后外参、遮挡 |
| 手部相机 | 一个手部 | 近距离观察、夹持检查、仓口对准 | 所在手臂、最短工作距离、夹爪可见性 |

**不要沿用“头部加左右腕部”的旧假设。** 这是部分参考项目的机位布局，尚不是当前用户描述的设备布局。

三个机位的优势主要是视角互补。是否有助于精度，需要看各自能观察什么、是否提供可用深度、是否有准确标定。

### 4.3 深度相机的角色

RGB图像回答“是什么、在哪一片图像区域”；深度和标定用于恢复目标在三维空间中的位置。

深度不直接给出完整的可执行抓取，也不自动保证毫米级插入。其有效性受距离、反光、遮挡、边缘混合、深度与彩图对齐、时序和标定误差影响。

首个版本应选择工作距离和目标区域内深度最可靠的一路作为主定位来源，其他视角按需补充。

### 5.1 本地：Qwen3.5-2B量化版

这是用户明确指定的本地试用候选，基础模型名称为`Qwen/Qwen3.5-2B`。

已确定的是模型系列与量化方向；以下内容尚未确定：

建议优先测试目标识别、颜色与类别判断、候选目标选择、结构化输出等范围明确的任务。先测通过哪些能力，再决定将哪些能力交给它。

### 5.3 两个模型的关系

当前选择表示“两个候选进入测试”，不表示最终必须同时运行，也不表示已实现自动切换。

建议在相同的真实比赛图像和任务集合上比较：

| 维度 | 应记录什么 |
|---|---|
| 目标选择 | 是否选对实例，而不仅是说对类别 |
| 颜色识别 | 光照、阴影、反光下是否混淆 |
| 空目标处理 | 目标不在画面中时是否能明确表示未找到 |
| 定位 | 框或点是否落在目标上，坐标规则是否正确 |
| 结构化输出 | JSON是否合法、字段是否稳定、是否可校验 |
| 工具调用 | 是否选择允许工具、参数是否符合约定 |
| 速度 | 完整请求的P50、P95和超时率 |
| 资源 | 本地峰值显存、内存与其他进程共存情况 |
| 费用 | 云端实际输入输出、重试和累计费用 |
| 失败处理 | 是否识别不确定性，是否重复无效操作 |

本地模型较小并不等于一定满足实时要求；云端模型有能力也不等于赛场网络一定稳定。

## 6. 总体架构

### 6.1 分层职责

| 层级 | 组成 | 主要职责 |
|---|---|---|
| 任务层 | Agent、任务状态机 | 目标理解、阶段管理、工具选择、结果检查、有限恢复 |
| 感知层 | 相机、Qwen、检测/分割、深度处理 | 识别、实例定位、目标区域、三维测量 |
| 抓取层 | GraspNet、AnyGrasp或几何方法 | 生成并筛选抓取候选 |
| 规划层 | 运动规划、IK、碰撞检查 | 将抓取及放置目标变成可执行路径 |
| 执行层 | X5、夹爪、升降、底盘SDK与驱动 | 执行控制并返回实际状态 |
| 协作层 | ROS2、工具API、日志 | 模块通信、坐标关系、请求反馈和证据记录 |

ROS2贯穿各模块；图中的分层是职责划分，不意味着每层都必须新建一个独立服务。

### 6.2 全链路示意

```text
裁判任务口令 / 任务输入
          |
          v
任务Agent + 状态机
  解释目标、调用工具、维护阶段、理解结果
          |
          v
场景采集工具
  RGB + 对齐深度 + 相机标定 + 当时机器人状态
          |
          v
Qwen视觉理解 + 必要的检测/分割
  目标实例、颜色、图像区域、可见特征
          |
          v
三维几何与目标点云
  数据有效性、坐标变换、场景关联
          |
          v
GraspNet / AnyGrasp / 任务几何候选
  接触位置、夹爪朝向、开口、候选分数
          |
          v
候选筛选 + IK + 轨迹规划 + 碰撞与约束检查
          |
          v
ROS2控制适配 + 厂家SDK/驱动
  X5、夹爪、升降、底盘
          |
          v
实际运动反馈 + 结果图像 + 抓持/放置检查
          |
          +--------------------> 返回任务Agent与状态机
```

### 6.3 两类反馈应同时保留

执行反馈：请求是否受理、轨迹是否结束、机械臂是否到位、夹爪是否达到目标开度、是否超时或停滞。

任务反馈：目标是否选对、是否确实夹住、是否搬运中滑落、是否插入正确仓位、释放后是否稳定。

运动结束与任务完成分别记录。末端位置正确不能单独证明物体状态正确。

## 7. Agent到底负责什么

### 7.1 当前想建立的Agent

Agent是面向比赛任务的上层协调者。它接收任务、使用观测与已确认的记录、选择允许工具、读取工具结果，再决定下一步。

其交互循环为：

```text
理解任务 -> 观察 -> 选择工具 -> 执行 -> 检查反馈 -> 继续 / 调整 / 结束
```

一次比赛任务通常保持同一个任务上下文，不需要每获取一帧图像就创建一个新Agent实例。

### 7.2 “调用工具”仍需要哪些判断

用户希望Agent主要调用已经实现的工具，而非承担全部抓取几何推导。可以据此明确分工：

- Agent判断目标、阶段和下一工具；
- 视觉与点云模块提供测量；
- 抓取模型提供候选；
- 本地筛选与规划器检查并组织执行；
- 厂家接口落实运动。

如果所有顺序和分支都由程序固定，执行者就是状态机；当模型根据语义、场景和结果选择工具时，属于Agent。两者可以共同组成任务层。

### 7.3 建议赋予Agent的职责

1. 将任务口令转成明确目标；
2. 在候选目标中选出符合任务的一项；
3. 调用观察、识别、抓取、导航、放置等工具；
4. 理解结构化执行状态；
5. 在允许范围内选择重新观察、换候选或重新规划；
6. 保留目标身份、任务阶段和当前物体关系；
7. 仅在有相应证据时报告完成。

### 7.4 精细运动应由本地工具承担

Agent输出的任务意图需要经过接口校验。连续关节控制、坐标变换、候选可达性、轨迹执行、反馈超时和中断，由本地程序落实。

初版不要求Agent临时编写几何计算代码或修改控制程序。新增能力通过实现和验证一个工具，再加入工具集合。

## 8. Agent、状态机、ROS2与SDK的关系

| 部分 | 决策对象 | 例子 |
|---|---|---|
| Agent | 语义和任务层选择 | 选红色电池；判断需要换个观察角度 |
| 状态机 | 流程阶段与前置条件 | 已确认夹住并收臂后才进入搬运 |
| ROS2 | 模块的数据、任务和状态交换 | 发布图像、传递轨迹、返回动作状态 |
| 规划器/控制器 | 运动解与执行过程 | 求解IK、检查轨迹、跟踪运动 |
| SDK/驱动 | 硬件命令与反馈 | 发送关节/速度指令、读取状态 |

ROS2中的回调调度与Agent的任务决策处于不同层次。ROS2不会自行理解“抓哪一块电池”；Agent也不会替代ROS2中的图像传输、坐标系统和控制节点。

Agent可以调用HTTP、Python或其他工具接口；工具内部再连接ROS2和厂家接口。初版优先接现有模块，避免让上层Agent再成为一个独立的硬件控制通道。

具体ROS2话题、服务、Action、节点名、QoS和ROS Domain，需按ROG现状盘点后确定。本文不虚构现有话题名称。

## 9. 视觉处理链路

### 9.1 任务指令与目标身份

首先明确电池类别、所需颜色、目标仓标识及规则要求，避免把同类别物体混成一个目标。

后续抓取、携带和放置应跟踪同一个目标身份。若遮挡或操作造成身份不确定，保留该状态，再选有用的观测恢复判断。

### 9.2 Qwen的输出范围

Qwen可以输出目标描述、颜色、候选编号、图像框或点，以及当前场景能否支持判断。具体使用哪一种输出，应通过离线验证选择。

建议优先考虑两种实现之一：

| 实现 | Qwen负责什么 | 其他模块负责什么 |
|---|---|---|
| 直接定位 | 对画面中的目标给出框/点 | 校验坐标、细分目标、恢复深度 |
| 候选选择 | 从检测器给出的候选中选择实例 | 检测器和分割器给出更细的几何区域 |

这两种实现均尚未最终选定。固定颜色任务中，经过验证的传统视觉也可承担部分识别工作。

### 9.3 图像坐标必须有完整定义

每个输出需要说明：

- 对应哪一个`camera_id`和`observation_id`；
- 对应的图像宽高；
- 使用像素坐标还是归一化坐标；
- 点是`[x,y]`还是`[row,col]`；
- 图像是否裁剪、缩放或去畸变；
- 如何还原到原始RGB和深度的对应位置。

不能把一种模型的坐标约定直接套到另一个模型，也不能把缩略图中的坐标直接索引原始深度图。

### 9.4 分割和深度筛选

目标框用于缩小搜索范围，分割用于尽量隔离目标表面。点云中应处理无效深度、背景、桌面、夹爪和邻近物体的影响。

同时保留独立的场景障碍表示。只裁出目标物体会丢失邻近物体、台面、机器人本体等碰撞信息。

分割方法、去噪、采样和点数等应依赖最终抓取模型的输入要求，本文不提前固定数值。

## 10. 标定、坐标与时间一致性

### 10.1 实施前需要明确的标定内容

| 标定/定义 | 用途 |
|---|---|
| 相机内参与畸变 | 像素与相机射线的关系 |
| RGB与深度对应 | 为选中的RGB区域取得正确深度 |
| 深度单位与尺度 | 将深度转换到统一长度单位 |
| 固定相机外参 | 相机与其安装参考坐标的关系 |
| 腕部手眼标定 | 末端/腕部与相机的固定关系 |
| 双臂安装变换 | 左右臂基座与整机参考系的关系 |
| 夹爪控制点/TCP | 轨迹实际控制的是哪个物理点 |
| 升降和头部运动关系 | 传感器或手臂随机构运动后的坐标更新 |

### 10.2 统一约定的建议

内部采用一个明确的长度、角度、姿态和坐标规范，在SDK边界做显式转换。建议以米和弧度为内部单位，但最终必须记录SDK真实要求。

以下问题要有唯一答案：

- 变换矩阵将源坐标映射到哪个目标坐标；
- 四元数顺序是`xyzw`还是`wxyz`；
- 欧拉角的旋转顺序及内外旋约定；
- 抓取模型中的夹爪轴与X5夹爪轴如何对应；
- 抓取候选的中心与X5控制点之间是否有偏移；
- 夹爪参数表示总开口、单指位移还是归一化控制量。

### 10.3 变换的基本形式

以下仅是约定示例：`T_A_from_B`表示把B坐标中的点转换到A坐标。

```text
p_base = T_base_from_camera * p_camera

T_base_from_grasp = T_base_from_camera * T_camera_from_grasp
```

腕部相机通常需要结合曝光时刻的机械臂状态：

```text
T_base_from_camera(t)
    = T_base_from_tool(t) * T_tool_from_camera
```

若安装结构还经过升降、头部转动或其他关节，需要把对应变换加入链条。机体上安装的相机不必然相对地面固定，也不必然相对双臂基座固定。

### 10.4 观测快照

建议以不可混用的观测记录绑定：图像、深度、标定、曝光/采集时间、机械臂状态、底盘/升降状态、状态版本和坐标系。

绑定记录不等于硬件同时曝光。适配层仍需处理传感器时间差、状态插值或静止采集条件，并记录能达到的同步质量。

旧观测可以保留作历史证据。重新执行动作前，应确认它所描述的物体和参考系几何关系是否仍有效。

## 11. 抓取链路

### 11.1 抓取模型负责生成候选

GraspNet/AnyGrasp等方法输入符合要求的点云，生成夹爪位置、方向、开口及模型定义的其他字段。

这些候选是待检查的方案。模型分数不自动等于真实抓取成功概率，排名最高也不一定最适合X5或后续插槽。

当前尚未最终决定：具体实现、检查点、输入相机、预处理、候选数量、筛选标准和推理设备。

### 11.2 候选筛选

建议至少考虑以下方面：

| 检查 | 要回答的问题 |
|---|---|
| 目标一致性 | 候选抓的是当前指定电池吗？ |
| 夹爪几何 | 开口、手指厚度和接触区域是否匹配？ |
| 接近路径 | 能否在闭爪前到达接触区域？ |
| IK与关节限制 | 哪条手臂能以允许姿态到达？ |
| 碰撞 | 手臂、夹爪、另一条臂及场景是否存在冲突？ |
| 后续携带 | 抓起后是否容易收臂、转向和稳定承载？ |
| 后续插槽 | 进入端是否露出，夹爪是否挡住仓口？ |
| 观测可信度 | 深度、标定和目标区域是否足够支持这次操作？ |

### 11.3 执行过程

抓取工具建议组织成如下阶段：

1. 选定候选及允许的接近方向；
2. 规划到预抓取位置；
3. 检查实际到位与夹爪开度；
4. 执行受限的最后接近；
5. 闭合夹爪；
6. 在允许条件下抬起或进行兼容的夹持验证；
7. 判断目标是否实际跟随夹爪；
8. 确认后进入收臂/携带阶段。

这些阶段是流程建议，具体距离、速度、容差与验证动作都需要实物试验后确定。

### 11.4 固定电池几何的作用

比赛电池形状固定时，可利用其尺寸、可夹区域和进入端约束筛选通用模型候选；也可建立几何基线，与学习型抓取检测比较。

这一点用于减少任务歧义，并不表示当前已经决定替换GraspNet路线。最终依据真实电池上的抓取、携带、插入表现选择。

## 12. 抓取结果验证

建议把“工具受理”“动作结束”“机械臂到位”“夹住物体”“携带成功”分别记录。

| 现象 | 能说明什么 | 单独不足以说明什么 |
|---|---|---|
| 闭爪指令成功返回 | 接口完成了一次调用或执行 | 电池已被可靠夹住 |
| 夹爪有非零开口 | 存在某种开口/受限状态 | 夹的是目标电池 |
| 腕部画面中有电池 | 电池在该视角可见 | 电池已经离开台面并跟随手运动 |
| 电池短暂随抬起运动 | 该段运动中保持了夹持关系 | 后续横移和越障不会滑落 |
| 放置点到位 | 机械臂接近计划目标 | 电池实际进入仓位并稳定 |

建议使用三态结果：`confirmed`、`contradicted`、`unresolved`。需要后续证据的结果继续保留不确定性，不用模型口头“看起来成功”替代物理状态证据。

多相机的价值在于解决具体疑问。例如，手部看夹持区域，胸前看目标是否离开原支撑面，而非每次都把三个完整画面全部发送给VLM。

## 13. 收臂、底盘与携带

### 13.1 收臂是操作与移动的衔接

抓住电池后，需要进入已验证的携带姿态，兼顾：

- 电池与夹爪保持；
- 重心、机械臂伸出和整机稳定性；
- 底盘通行范围；
- 相机视野；
- 另一条机械臂与升降机构的位置；
- 到终点后是否能恢复操作姿态。

携带姿态是待验证的机器人动作能力，本文不指定关节角。

### 13.2 底盘任务应独立实现并提供工具接口

任务Agent可以请求到达某个已定义区域或位姿，由本地导航/底盘程序执行。是否使用Nav2、已有导航栈或其他方法，需依据机器人现有软件和赛道确定。

激光雷达、里程计和导航等传感数据主要在本地链路处理。云端VLM按任务需要获取图像或简化场景信息，不默认上传完整雷达点云。

### 13.3 持物通过障碍区

静止桌面抓取通过之后，还要分别验证平地移动、转向、启停和障碍区对夹持的影响。

障碍区后的检查应能够发现滑移、方向变化或夹持关系丢失。若几何关系发生变化，后续仓口对准应使用新的观测。

## 14. 目标仓定位与插入

### 14.1 插入应单独验证

通用抓取检测主要解决取物接触候选。插入还需要明确电池进入端、仓口、轴线、相对倾角、可用间隙和稳定终点。

机器人到达区域或夹爪到达某个点，均不能单独证明完成插入。

### 14.2 建议阶段

| 阶段 | 任务 |
|---|---|
| 仓位识别 | 选对指定仓位和颜色/编号 |
| 粗对准 | 底盘、升降和手臂进入操作范围 |
| 相对位姿估计 | 重新观察电池进入端与仓口 |
| 精对准 | 修正位置、方向与倾斜 |
| 受限进入 | 使用经验证的控制与检查推进 |
| 到位判断 | 依据相对几何和有效反馈确认进入程度 |
| 释放与撤离 | 避免把电池带出或碰偏 |
| 稳定观察 | 对照规则确认释放后稳定3秒 |

是否使用视觉伺服、几何轨迹、接触检测或柔顺控制，需要结合实机接口确定。本文不假定机器人已有力传感或力控能力。

### 14.3 数据和控制边界

深度缺失、反光、窄缝和遮挡可能使最后阶段比桌面抓取更困难。相机看不见的关系需要其他有效观测或已有证据支持。

运动停滞只说明未继续取得计划中的进展，不能自动认定已经插到底。对不明阻塞，需要检查错位、碰边、夹持滑移或支撑变化。

## 15. 完整任务状态机建议

以下是流程骨架，状态名是本文建议名称，不是当前ROG已存在的代码或ROS2接口。

```text
IDLE
  -> TASK_ACCEPTED
  -> OBSERVING_PICK_AREA
  -> TARGET_IDENTIFIED
  -> GRASP_CANDIDATE_READY
  -> APPROACHING
  -> GRASPING
  -> VERIFYING_HOLD
  -> STOWING_FOR_CARRY
  -> NAVIGATING
  -> ARRIVED_AT_PLACE_AREA
  -> OBSERVING_SLOT
  -> ALIGNING
  -> INSERTING
  -> RELEASING_AND_WITHDRAWING
  -> VERIFYING_STABILITY
  -> COMPLETED
```

异常分支可进入重新观察、重新生成候选、重新规划或停止状态。分支应依据可检查的反馈触发，避免只按一次模型生成的长动作列表一路执行。

| 阶段 | 依赖的已确认条件 | 应保存的结果 |
|---|---|---|
| 开始抓取 | 任务目标和观测关联有效 | 目标ID、观测ID |
| 执行候选 | 候选和计划通过本地检查 | 候选ID、计划ID |
| 开始搬运 | 已确认夹持且携带姿态完成 | 抓持状态、实际姿态 |
| 开始插入 | 仓位正确、相对几何有效 | 仓位ID、对准证据 |
| 释放 | 满足已验证的放置/支撑条件 | 实际释放与撤离结果 |
| 报告完成 | 路径、仓位、插入及稳定条件均满足 | 完成证据链 |

具体重试次数、时间预算、停止条件和恢复范围尚未确定。

## 16. 建议工具集合

### 16.1 第一阶段工具

| 工具示例名 | 职责 | 返回重点 |

## 18. 云端与本地部署

### 18.1 建议保留在ROG的工作

- 相机、雷达与机器人状态采集；
- ROS2通信和TF坐标关系；
- 数据预处理、目标点云和几何计算；
- 抓取候选生成或其客户端；
- IK、规划、碰撞检查及轨迹执行；
- 任务状态、请求记录、执行反馈和中断；
- 本地模型推理或其服务；
- 必要的监控和日志。

最终哪些计算使用CPU/GPU，要根据实测分配。不能只按模型文件大小预算显存。

### 18.2 云端调用方式建议

只在需要的任务阶段发送图像和结构化上下文，例如选择目标、重新识别仓位、分析异常。需要跨视角判断时，再明确标注各机位提供多张图像。

默认不需要连续上传三路原始视频，也不需要把原始雷达点云传到云端。上传频率、压缩和分辨率需以目标识别效果与延迟共同确定。

### 18.3 网络预算

此前问卷中提出的上下行各约20Mbps属于需求建议，不是模型的固定最低带宽。

应测量：图片编码与上传、排队、模型处理、完整结果下载、结构化解析，以及失败重试的总时间。延迟波动和掉线通常与平均带宽同样重要。

如后续改为多路实时视频或远端点云处理，需要重新评估网络。当前方案优先利用本地传感与控制链路。

### 18.4 云端异常与本地候选

本地Qwen3.5-2B可以作为离线候选进入测试，但当前尚未建立自动降级能力。

仅在本地路径通过对应能力测试后，才把它定义为某些任务的备用执行路径；无法确认目标时，应保持目标未决，不自行假定云端结果。

## 19. 失败恢复与执行一致性

### 19.1 超时不等于动作未执行

每次物理操作保留请求ID和执行记录。通信超时后先查询该请求的状态，避免重新发送同一操作而导致重复运动。

图像保存失败、日志写入失败和模型请求失败，也不能反向证明已经确认的物理操作没有发生。

### 19.2 按实际失败阶段处理

| 失败阶段 | 建议检查方向 |
|---|---|
| 目标未找到 | 指令、候选区域、遮挡、光照和观察角度 |
| 深度不可用 | 距离、反光、RGB-D对应、缺失区域和外参 |
| 无可用抓取 | 候选生成、夹爪匹配、遮挡和任务约束 |
| 规划失败 | 可达性、关节限制、障碍物与另一条臂 |
| 闭爪为空 | 接触几何、坐标、实际到位与目标变化 |
| 抬起后滑落 | 夹持部位、接触、载荷与姿态 |
| 携带中变化 | 底盘运动、振动、夹持变化和携带姿态 |
| 插入受阻 | 相对错位、倾斜、进入端、仓口和支撑变化 |
| 释放后不稳定 | 插入程度、支撑、夹爪撤离和道具几何 |

这些是待验证的诊断方向，不是未经观测即可认定的原因。

### 19.3 并发的适用范围

独立的图像分析、已有快照几何计算和日志处理可以考虑并行。共享机械资源或依赖前一物理结果的动作应保持顺序。

例如，未确认夹持成功前不进入依赖该结果的搬运阶段。队列取消与正在运行的物理动作中断要分别定义。

## 20. 与uni-robot-agent的对照

### 20.1 核心区别

| 项目 | uni-robot-agent的公开Direct思路 | 当前团队选择 |
|---|---|---|

1. 图像、深度、标定、状态绑定到同一快照；
2. 工具采用明确参数、单位与结构化返回；
3. 动作反馈保留实际到位、误差和停止原因；
4. 网络异常后查询回执而非盲目重放；
5. 抓取、插入等经验整理成可查阅文档；
6. 记录工具调用、图片、时间线和模型交互；
7. 将动作完成与任务完成分开。

## 23. 分阶段验证建议

以下是为当前方向整理的推进顺序，尚不是已经执行完的计划，也不包含机器人启动命令。

### 阶段A：设备与接口盘点

记录实际型号、ROG运行环境、GPU与空闲资源、相机序列号与安装位置、可用流、X5/夹爪/底盘/升降接口、已有ROS2节点和控制所有者。

产出：设备清单、接口清单、坐标关系草图、软件版本记录。

### 阶段B：视觉离线对比

用真实机位拍摄电池和仓位，包含光照变化、不同摆放、遮挡和目标不存在。对同一批图像测试两个已选Qwen候选。

产出：目标选择、定位、拒答、解析、延迟、显存和费用记录。先进行不发运动指令的验证。

### 阶段C：标定与三维定位

完成所需标定，在机器人工作区比较可测参考与重建位置。分别检查不同距离、机位、头部/升降/腕部状态下的误差。

产出：标定文件、验证样本、误差统计、有效工作范围和失败条件。

### 阶段D：抓取候选离线检查

对保存的RGB-D样本生成候选，检查单位、轴向、控制点、夹爪宽度和接近方向，叠加显示候选与场景。

产出：已核对坐标的候选、可达性与碰撞检查结果。候选可视化正确后再安排实机验证。

### 阶段E：静止单臂拾取与放回

验证目标选择、接近、闭爪、抬起、确认夹住及放回。记录真实电池类别和重量，不混用不同道具条件的结果。

产出：分阶段结果、失败样本、可重复的已验证动作条件。

### 阶段F：携带与底盘

逐步加入收臂、平地移动、转向、启停和赛道障碍条件，检查持物关系与整机状态。

产出：携带姿态、导航/底盘接口验证与滑落记录。

### 阶段G：仓口对准与插入

先独立验证仓位识别和相对几何，再验证对准、进入、释放、撤离与3秒稳定。

产出：进入端和仓位模型、相对定位误差、插入结果与恢复条件。

### 阶段H：全流程联调

按正式任务顺序运行，记录每阶段耗时、完整完成率、掉落、错位和网络异常。全过程以真实反馈推进。

产出：可回放记录、端到端指标和仍待解决的问题列表。

## 26. 当前期待与能力边界

### 26.1 期待达到的效果

- 通过自然语言或规定格式给出比赛任务；
- 机器人自主选中指定目标；
- 利用实际视觉和三维几何适应一定位置、朝向变化；
- 专用抓取模块给出可用候选；
- Agent调用已实现工具，依靠反馈完成任务；
- 携带通过障碍区域后重新检查目标状态；
- 在正确仓位完成插入与稳定释放；
- 对错误、未决与失败有记录和受限处理流程。

### 26.2 当前不作为前提的能力

- 任意物体、任意环境下均可抓取；
- 三个相机自动提供更高精度；
- 单个模型同时解决感知、控制、导航和插槽；
- 小型本地VLM天然等同于论文中的完整机器人Agent；
- 桌面拾取成功即可推出越障持物和插入成功；
- 参考项目的仿真、演示或评分可直接代表本机能力。

### 26.3 当前方案的一句话描述

**基于方舟无限LIFT2s和X5双臂，建立一个工具驱动的任务Agent；使用Qwen进行指令与视觉理解，使用深度相机、标定及点云抓取模型计算和筛选抓法，由本地规划、ROS2与厂家接口执行，并通过多视角和实际反馈完成闭环。**

## 30. 本次新增决策与验证计划

**新增时间：2026-11-06 22:35（UTC+08:00，Asia/Hong_Kong）。**

本节对应用户本次确认的三项调整。前文第29节记录的是初版编写范围；本节来自后续讨论和本次只读核查。以下闭环、回退及模型路线均属于待实现、待验证的计划，不能作为现有实机能力。Qwen3.8-Flash 云端看图和只读工具调用已有先前测试记录，具体候选筛选接口尚待实现。

### 30.1 新增：本地候选检测后，由Qwen进行语义筛选并闭环复核

**本项新增时间：2026-11-06 22:35（UTC+08:00）。用户已确认纳入计划。**

主路径采用“本地候选 → Qwen筛选 → SAM2分割 → 几何检查 → 新观测复核”。本地候选可来自当前YOLOE，或后续对比中的Grounding DINO。二者的最终选择依据同批实拍数据，暂不预设优胜者。

1. 建立不可变观测，保存原始RGB、可用的同帧深度、内外参版本、机器人关节状态、相机姿态与时间戳。用 observation_id 关联后续所有结果。
2. 本地检测器给出候选编号、原图像素框、检测分数和模型版本。候选数量过多时，由本地程序按工作区域和几何条件预筛选，保留可追溯编号。
3. 向Qwen提供任务要求、已确认的道具参考照片、现场全景，以及编号后的候选图。需要区分道具、电池架、泡沫件及其他相似白色物体。
4. Qwen返回候选编号、判定依据和结果状态。结果状态至少包括 selected、not_found、ambiguous。允许明确拒绝选择。模型给出的自评置信度仅供记录，不能直接当作标定概率。
5. selected进入SAM2分割，其他状态进入重新观测或第30.2节回退。分割后检查覆盖范围、背景泄漏、可见部件、深度有效率和尺寸一致性。
6. 把分割叠加图及几何检查结果交给Qwen复核目标身份；通过后进入位姿或抓取候选计算。语义判定与几何检查共同构成结果，任一项不确定均保留原因。
7. 执行动作后重新取图和读取执行回执，检查是否真正夹住、是否滑移、目标仓是否正确以及释放后是否稳定。需要修正时回到新观测，避免反复使用动作前的旧框。

输入输出需要统一原图尺寸、坐标顺序、裁剪偏移和缩放映射。项目内原图框使用 xyxy、点使用 [x,y] 时，接入上游 locate 的 [row,col] 必须显式转换。道具参考图片单独标注为参考证据，避免与实时观测混淆。

验证分两阶段进行。先在冻结图片上比较YOLOE单独检测、DINO单独检测，以及分别接入Qwen筛选后的误检、漏检、选错目标、正确拒绝与耗时。再进行现场只读闭环，测试背景、距离、光照、姿态、遮挡、多个相似物体和无目标场景。运行记录包含模型原始输出与最终筛选结果，防止通过只展示成功样本得出结论。

### 30.2 新增：零候选时，Qwen粗定位后接SAM2的回退路径

**本项新增时间：2026-11-06 22:35（UTC+08:00）。用户已确认纳入计划。**

当本地候选为零，或候选全部被语义复核拒绝时，允许Qwen结合参考照片在原始现场图上提出粗框或正提示点，再由SAM2分割。此回退与第30.1节的候选筛选主路径分别记录和评测。

1. 检查当前图像新鲜、目标所在区域可见，并提供清楚的道具参考照片。
2. Qwen返回 found、ambiguous 或 not_found；found时携带原图尺寸、粗框/点、可见性说明和对应 observation_id。
3. 校验坐标范围、面积和裁剪映射，向SAM2提供提示。粗框或点仅用于分割初始化。
4. 检查分割叠加图、目标身份及有效深度。对孔洞和白色背景分别检查，避免从孔内背景取深度。
5. 若分割或几何不可信，重新观测或尝试另一路有效视角。若需要改变观察姿态，由既有规划/执行服务处理运动，并在完成后建立新观测。
6. 重试次数和时间预算在现场测试后确定，并作为显式配置记录。预算耗尽时返回明确阻塞状态，任务进度和观测记录保留。

此路径重点测量零候选样本的补检率、错误补检率、分割质量、额外云端耗时和无目标时的正确拒绝率。Qwen的粗定位通过验证后，才进入第30.3节的空间计算。

### 30.3 新增：CAD位姿路线与点云抓取路线分开验证

**本项新增时间：2026-11-06 22:35（UTC+08:00）。用户已确认两路分别测试。**

最终赛事电池与现有CAD的一致性未知。当前CAD作为候选几何资料保存，不能直接当作最终实物真值。本次将两条路线并列进入验证，更新前文“抓取候选优先由GraspNet等生成”的单一路线表述。最终根据实物和比赛闭环表现决定主用路线。

| 项目 | 路线A：FoundationPose＋CAD抓取模板 | 路线B：GraspNet／AnyGrasp点云抓取 |
|---|---|---|
| 核心输出 | 电池整体位置和朝向，再转换CAD上的指定抓取部位 | 夹爪候选位置、朝向、开口及模型定义的评分 |
| 主要输入 | 目标掩膜、RGB-D、内参和尺寸正确的CAD网格 | 目标点云、深度单位、相机信息和夹爪约束 |
| 对最终道具的要求 | 先核查CAD外形、尺寸、孔位与实物一致性 | 实物需要有足够可信的可见点云，候选须适配夹爪与任务 |
| 把手抓取 | 在CAD上定义夹持横梁和接近方向，结合位姿转换 | 以把手区域及接近方向筛选候选，检查孔内背景干扰 |
| 主要不确定项 | CAD失配、对称朝向混淆、遮挡、表面深度缺失 | 候选在X5上不可达、碰撞、握持姿态妨碍后续插入 |

路线A测试顺序：核对STL/STEP的单位和原点 → 测量当前道具并比较关键尺寸 → 用离线RGB-D与掩膜做初始位姿估计和跟踪 → 检查CAD重投影、孔位及抓取模板的位置 → 完成手眼与TCP核验后，进入受控单臂抓取测试。若最终道具与CAD不一致，先评估重建/更新模型成本。FoundationPose的无CAD参考视图路线单独评估，不默认几张普通照片已满足建模输入。

路线B测试顺序：接入原始对齐深度 → 分割目标并提取点云 → 各模型生成候选 → 筛选夹爪开口、把手区域、接近方向、IK与碰撞 → 检查持物后收臂、携带和插入的姿态条件 → 进入受控抓取测试。AnyGrasp授权与运行环境单独核实。

两路先共用同一批冻结RGB-D、目标掩膜、标定版本、实物摆放和夹爪参数，分别记录失败，再比较：有效候选率、可达率、定位/朝向误差、抓起后保留、携带稳定、目标仓对准、插入与释放成功率、端到端耗时、GPU显存峰值。无几何真值时只报告重投影或重复性，避免将其命名为绝对精度。验收阈值根据实物公差和现场测量确定，尚无预设通过结论。

FoundationPose与GraspNet的接口职责不同。路线A通过“位姿＋已定义抓法”形成抓取目标，路线B直接提出抓取候选。即便路线A通过，插入仍需定位仓口、观察电池与夹爪的实际关系，并进行视觉/执行反馈闭环。

### 31.6 同样值得复用的底层机制与现有缺口

- 不可变图像/标定/机器人状态快照，及历史图像窗口管理。只保留必要新图，点云与原始深度留在本地，向Qwen返回必要几何摘要和证据索引。
- 按资源顺序执行、后台任务回执、重复请求识别和未知执行结果恢复。模型一次提出多个调用与实际执行并发分别配置。当前arxgent按顺序执行，不据此宣称已具备上游后台流水线。
- 参数Schema、物理单位、图像与坐标约定、实际位姿/开口反馈、pose_reached和stop_reason。工具成功、Agent结束、比赛任务完成分别记录。
- X5注册夹持参考点、夹爪开合轴与TCP转换说明。上游名义网格计算值只作为核验方法参考，必须核对我方真实夹爪、URDF与实测TCP。
- SAM3服务与模型批处理边界可以借鉴，选择SAM2时复用工具契约并适配后端；安装SAM3不是本次计划更新的前提。
- Code-as-Policy可供以后编写几何分析和工具编排程序时参考。比赛Agent是否允许自由代码执行另行设计，当前不默认开放shell。
- 上游通用工具没有提供可直接用于我方轮式底盘越障的导航、升降控制或专用电池插入与成功验证服务。GraspNet、AnyGrasp与FoundationPose也不能因为存在locate或grasp工具就视作已接入。需要在本项目分别实现对应适配与验收。

第一阶段建议顺序为 capture_scene/view_env_state 的接口映射 → locate(pixels/segment)与Qwen选择结果 → 受控move/grasp/release和执行回执 → 后台任务管理。triangulate在至少两路外参和同步条件满足后启用。每一步经过验证后再扩大能力。
